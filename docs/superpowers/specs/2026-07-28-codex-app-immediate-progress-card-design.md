# Codex App 即时进度卡设计

## 背景与目标

Youc 使用 Codex App（app-server）处理长任务时，如果模型迟迟没有产生可见输出，用户无法确认消息是否已经被接收。目标是在 Botmux 完成权限与路由校验后、把消息交给 Codex App 前，立即创建一张状态卡；后续真实进展持续更新同一张卡，任务结束后状态卡收口，最终答案仍单独发送。

首期只对显式开启配置的 Codex App 机器人生效，Youc 作为唯一灰度对象。功能默认关闭，不改变其它机器人和 CLI 的行为。

## 方案比较

### 方案一：Botmux 核心薄补丁

daemon 在消息准入后立即建卡，worker 把 Codex App 的真实进度回传给 daemon，由 daemon 串行更新原卡。该方案能保证首响时机，并可复用 Botmux 的会话持久化、飞书卡片和 Codex App 事件链路。

这是选定方案。

### 方案二：外部 Lifecycle Hook 服务

外部服务订阅 `topic.new`、`thread.reply` 等事件并调用飞书接口。该方案不修改核心，但需要自行处理机器人凭据、消息锚点、卡片消息 ID、重启恢复和并发去重，且 Hook 失败与主链状态难以保持一致。

### 方案三：仅通过 Prompt 要求模型先汇报

不修改 Botmux，但首响仍依赖模型调度和输出，不能满足“收到消息后马上反馈”的硬要求。

## 配置

在机器人配置中新增可选布尔字段 `codexAppImmediateProgressCard`：

- 缺省或 `false`：完全保持官方行为。
- `true` 且 `cliId` 为 `codex-app`：启用即时进度卡。
- 非 `codex-app` 机器人即使误配也不启用，并记录诊断日志。

首期只要求配置文件支持，不增加 Dashboard 配置界面，减少与官方代码的冲突面。

## 数据流

1. daemon 收到新话题或已有话题回复。
2. 权限、路由、会话状态和消息准入检查通过。
3. 若当前机器人启用本功能，为本次逻辑任务创建进度状态：
   - 标题：`处理中 · <用户消息摘要>`
   - 正文：`已收到，开始处理。`
   - 阶段：`running`
4. daemon 立即回复交互卡，并记录卡片消息 ID。
5. 用户消息继续进入现有 Codex App turn/steer 流程；首响卡失败不得阻塞消息投递。
6. app-server 产生 assistant commentary/progress 后，worker 将真实进展发送给 daemon。
7. daemon 对进展去重、增量追加，并 PATCH 已记录的原卡片。
8. 正常完成时先把状态卡更新为 `已完成`，再走现有最终答案发送链路；异常、中断或关闭时把状态卡更新为相应终态。

运行中 steer 属于当前逻辑任务，继续更新当前卡；只有真正进入后续排队任务或新的空闲后回合时才创建新卡。

## 状态与并发

每个会话只保存当前逻辑任务的进度卡状态：

- 逻辑 turn ID
- 飞书卡片消息 ID
- 已累计正文
- 当前阶段：`running`、`completed`、`failed`、`interrupted`
- 最近一次进度指纹

同一张卡的 POST/PATCH 操作使用 Promise 链串行化，避免多条进展同时判断“尚无 messageId”而重复建卡。连续相同进度不追加；不同进度按到达顺序累积。

状态写入现有 session store。daemon 重启后优先继续 PATCH 原卡；若原卡已撤回，下一次真实进展最多重建一次并更新状态。

## 卡片内容

运行中示例：

```text
处理中 · 检查 Botmux 部署

已收到，开始处理。

已确认当前运行版本。

正在核对自定义补丁。
```

成功终态：

```text
已完成 · 检查 Botmux 部署

已收到，开始处理。

已确认当前运行版本。

正在核对自定义补丁。

任务已完成，结果见下方最终回复。
```

进度内容沿用现有 Markdown 消毒和长度限制，不把命令参数、凭据或完整工具输入直接写入卡片。

## 错误处理

- 首卡发送失败：记录日志并继续执行任务；后续真实进度可再次尝试建卡。
- PATCH 临时失败：保留状态，下一条进度继续尝试。
- 卡片被撤回：清除失效消息 ID，最多重建一次。
- 会话关闭、worker 异常退出或用户中断：尽力写入对应终态；失败不阻塞现有清理流程。
- 最终答案发送失败：不把进度卡误标为“答案已送达”，终态文案只说明任务计算阶段已经结束。

## 测试与验收

定向单元测试覆盖：

- 开关默认关闭，仅对启用的 `codex-app` 生效。
- 消息准入后、worker 投递前创建首卡。
- 首卡失败不阻塞用户消息。
- 同一任务只 POST 一次，后续进展 PATCH 原卡。
- 进展增量追加、重复去重、PATCH 串行。
- steer 复用当前卡，下一逻辑任务创建新卡。
- 成功、失败、中断分别写入正确终态，最终答案仍走独立消息。
- daemon 重启恢复原卡状态，撤回后最多重建一次。

候选版本只构建和测试，不直接替换线上官方 3.6.0。部署需要单独确认，且先只给 Youc 灰度；验证首响、持续更新、终态和最终答案四个环节后再决定是否长期使用。

## 官方同步策略

实现分支从官方 `v3.6.0` 创建，只包含本设计、必要代码和测试。旧 `dev` 分支仅作为行为参考，不直接合并。后续官方升级以新稳定 tag 合入本分支，冲突范围应限制在配置解析、消息准入、Codex App 进度桥和卡片状态管理几个明确边界内。
